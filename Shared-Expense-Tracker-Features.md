# Shared Expense Tracker — Overall Features

## Overview
A collaborative expense tracking application for families, roommates, or groups. Users can create or join groups, manage shared expense lists, add expenses, mark them as paid/unpaid, and view summaries of unpaid amounts. The **first (default) list is created by the group creator** (not auto-generated by the system), so the name and purpose of the primary list are fully dynamic.

---

## Core Concepts
- Multiple people (family / roommates) can share expense lists.
- When a group is created, the **group creator defines the first (default) list** — name and purpose are chosen by the user (e.g. “Monthly Bills”, “Rent & Utilities”, “Household”, etc.).
- Users can create additional custom lists (e.g., shopping, utilities, necessities).
- Inside any list, members can add expenses that need to be paid.
- Expenses can be marked paid or unpaid, which updates the total amount.
- All members of a group can view and update lists in real time.
- Users can check a summary of unpaid expenses.

## Core Features

### Authentication
- **Register** new user
- **Login**
- **Get current user profile** (`/auth/me`)

### Groups
- **Create Group** — group creator then creates the first (default) list
- **List all groups** the current user belongs to
- **Get group details + members**
- **Join Group** via share code / shared link
- **List members** of a group

### Expense Lists
- **Create the first (default) list** — done by the group creator after creating the group (name is dynamic)
- **View all lists** in a group (default + custom)
- **Create custom list**
- **Get a single list** + its expenses
- **Update list name**
- **Delete a custom list** (default/primary list cannot be deleted, or deletion is restricted)

### Expenses
- **Add expense** to a list
- **Mark expense as paid or unpaid** (adjusts amount / totals accordingly)
- **View expenses** within a list
- **Show unpaid total / summary** of unpaid expenses

---

## Application Flow
1. User registers / logs in.
2. User lands on **Group Dashboard**.
3. User can either:
   - **Create a new group** → enters group name → enters **Group View** → **group creator creates the first (default) list** (chooses name & purpose) → proceeds with list management.
   - **Join an existing group** → enters shared code → system validates code → if valid, enters **Group View**; if invalid, shows error and returns to dashboard.
4. Inside **Group View**, user can:
   - Create additional custom expense lists.
   - View an existing expense list.
5. Inside a list, user can:
   - Create a new expense.
   - Mark expenses as paid or unpaid.
   - View unpaid total / summary.
6. Changes are visible to all group members.

---

## Data Store
- **UserData** — user accounts and profiles
- **Group Data** — groups, members, share codes
- **List Data** — expense lists belonging to groups (first list created by group creator is treated as primary/default; additional lists are custom)
- **Expense Data** — individual expenses (amount, paid/unpaid status, etc.)

## API Endpoints Summary

### Auth
| Method | Endpoint          | Description                  | Auth |
|--------|-------------------|------------------------------|------|
| POST   | `/auth/register`  | Register new user            | No   |
| POST   | `/auth/login`     | Login                        | No   |
| GET    | `/auth/me`        | Get current user profile     | Yes  |

### Group
| Method | Endpoint                    | Description                                      | Auth |
|--------|-----------------------------|--------------------------------------------------|------|
| POST   | `/groups`                   | Create a new group (no auto list)                | Yes  |
| GET    | `/groups`                   | List all groups the current user belongs to      | Yes  |
| GET    | `/groups/:groupId`          | Get group details + members                      | Yes  |
| POST   | `/groups/join`              | Join a group using share code                    | Yes  |
| GET    | `/groups/:groupId/members`  | List members of a group                          | Yes  |

### Group Expense Lists
| Method | Endpoint                    | Description                                      | Auth |
|--------|-----------------------------|--------------------------------------------------|------|
| GET    | `/groups/:groupId/lists`    | Get all lists in a group (primary + custom)      | Yes  |
| POST   | `/groups/:groupId/lists`    | Create a list (first list becomes primary/default; subsequent are custom) | Yes  |
| GET    | `/lists/:listId`            | Get a single list + its expenses                 | Yes  |
| PUT    | `/lists/:listId`            | Update list name                                 | Yes  |
| DELETE | `/lists/:listId`            | Delete a custom list (primary/default list cannot be deleted) | Yes  |

> **Note:** Expense-specific endpoints (create expense, mark paid/unpaid, summary) are implied by the product requirements and flowchart but were not fully listed in the provided Endpoints spreadsheet. They should be added under an Expense resource.

## Frontend Build Instructions (ASP.NET Core Web MVC)

### Technology Stack
| Layer              | Technology                          | Purpose |
|--------------------|-------------------------------------|---------|
| Framework          | ASP.NET Core Web MVC                | Server-rendered views + controllers |
| Styling            | Tailwind CSS                        | Responsive, utility-first, clean UI |
| HTTP Client        | Axios                               | All API calls (CRUD, auth, errors) |
| Real-time          | SignalR                             | Live unpaid-expense count updates |
| Charts             | ApexCharts                          | Simple unpaid expense summary chart |
| Data Passing       | **ViewData only**                   | Strictly no ViewBag |

### Core Rules
1. **ViewData only** — Controllers must pass data exclusively via `ViewData["Key"]`. Do **not** use `ViewBag` or strongly-typed models for view data.
2. **Tailwind CSS** — All styling via Tailwind utility classes. Keep layout mobile-first, responsive, tidy, and clean.
3. **Axios** — Centralize API calls in a shared JS module. Handle loading, success, and error states consistently.
4. **SignalR** — Connect to a hub that broadcasts unpaid-count changes. When an expense is marked paid → decrease count; marked unpaid → increase count. Update badge/counter in real time for all group members.
5. **ApexCharts** — Use a simple bar or donut chart on the unpaid summary view. Keep configuration minimal and readable.
6. **UI/UX** — Clean hierarchy, consistent spacing, clear action buttons, helpful empty states, and accessible labels. Prefer card-based layouts and subtle shadows over heavy decoration.

### Axios Patterns
- Base instance with auth token interceptor.
- Dedicated methods: `login()`, `register()`, `createGroup()`, `joinGroup()`, `getLists()`, `createExpense()`, `togglePaid()`, `getUnpaidSummary()`, etc.
- Always show loading indicator and user-friendly error toast / message.

### SignalR Real-time Unpaid Count
- Hub name suggestion: `ExpenseHub`.
- Events:
  - `UnpaidCountChanged(groupId, listId, newCount)`
  - Client joins group/list groups on page load.
- On `togglePaid` success → server pushes new count → all connected clients update the badge and (optionally) the chart.

### ApexCharts (Unpaid Summary)
- Simple donut or horizontal bar showing unpaid vs paid totals (or breakdown by list).
- Initialize once on the Summary page; update data live via SignalR if desired.
- Keep options minimal: clean labels, consistent colors, responsive container.

### UI/UX Guidelines
- **Layout**: Sticky top nav with logo + user menu + real-time unpaid badge.
- **Cards**: Soft rounded cards with subtle border/shadow for groups, lists, and expenses.
- **Actions**: Primary (blue/indigo) for create/save, secondary (gray) for cancel, danger (red) for delete.
- **Empty states**: Friendly illustration or icon + short message + CTA button.
- **Forms**: Clear labels, Tailwind form controls, validation messages under fields.
- **Responsive**: Mobile-first; stack cards on small screens, side-by-side on larger screens.
- **Feedback**: Toast notifications for success/error; disable buttons while submitting.
- **Accessibility**: Proper contrast, focus states, aria labels on interactive elements.

### Implementation Order (Recommended)
1. Scaffold MVC project + Tailwind + Axios + SignalR + ApexCharts.
2. Auth views (Login / Register) + Axios auth flow + store token.
3. Group Dashboard (list groups via ViewData) + Create / Join.
4. Group Details → Lists overview.
5. List Details → Expenses table + Add Expense + Mark Paid/Unpaid.
6. Wire SignalR for live unpaid count badge.
7. Unpaid Summary page with ApexCharts.
8. Polish UI (spacing, empty states, loading skeletons, toasts).

### Notes
- Primary/default list cannot be deleted (enforce in UI + API).
- All real-time updates must be scoped to the current group (and preferably list).
- Keep JavaScript modular and free of inline business logic in views where possible.
- Prefer progressive enhancement: pages should still work without SignalR (static counts), but live updates improve UX.
